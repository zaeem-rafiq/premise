# Platform measurements, 2026-10-04

These measurements decide the "decided by spike" items of
[`docs/spec/01-core.md`](../../spec/01-core.md) section 15.

- **Where:** a Cloudflare account on the Workers Paid plan, Artifacts open beta.
- **How:** a throwaway Worker with one SQLite-backed Durable Object, deployed
  with wrangler 4.147.0 and called over HTTPS. The harness is in
  [`reference/artifacts-spike/`](../../../reference/artifacts-spike/). Its 171
  local tests check the hand-built pack and the receive-pack request against
  real git.
- **Limits of this evidence:** every experiment ran once, from one location,
  on small repositories (a few files). Latency is a single sample set, not a
  benchmark. All test repositories and both test Workers were deleted afterwards.

## Decisions

| Item | Decision | Evidence |
| --- | --- | --- |
| Push path | Trunk builds the pack by hand and posts `git-receive-pack` itself. No git client library on the landing path. | E8: single-ref and two-ref pushes accepted; the binding reads the hand-built objects. |
| Atomic landing of `main` and `refs/notes/premise` | One request with two commands. | E8: with one wrong old id, the server refused both commands, in both command orders, with and without the `atomic` capability (which is not advertised). |
| Compare-and-swap | The server checks the old object id. | E3 and E8: a fast-forward update with a stale old id was refused with `stale ref`; the same update with the correct old id was then applied. |
| Token | Tokens from `createToken()` work from inside a Durable Object. | E2: write and read tokens accepted with Bearer and Basic auth, inside and outside Workers. workers-sdk issue 15429 did not reproduce. |
| Who may hold a write token | Only Trunk. | E3: any write token can force-push and delete branches, including the default branch. Agents never receive a write token for a pool repository. |
| Attempt repositories | Forked off the landing path, at most four at a time, with retry. | E5: 20 concurrent forks gave 15 usable and 5 failures (`INTERNAL_ERROR` 10400); ready in 1.7 to 4.0 s (p50 3.4 s). `fork()` returned no usable token, so `createToken()` is needed. |
| Serving pool files | By commit id through the binding. | E4 and E6: `readFile({ ref: <commit id>, path })` returned the file for every ref tested. |
| Verification runtime for the green line | A Dynamic Worker isolate (Worker Loader binding). No container. | Sandbox test below. |
| Workhorse coding model | `@cf/openai/gpt-oss-120b`, with `@cf/moonshotai/kimi-k2.7-code` for races. | E9 below. Real seeded intents are still to be measured. |
| Typed judgments | Clef works for premise triage. | Clef test below. |

## E1 to E8: Artifacts from inside a Durable Object

| Experiment | Result |
| --- | --- |
| E1 create and push | `create()` to ready: 1.3 to 2.7 s. Push with the `create()` token: 168 to 245 ms. The binding saw the new head 28 ms later. |
| E2 minted token | `createToken()` took 42 to 44 ms. Pushes with a minted write token: 125 to 137 ms. A read token cannot push. |
| E3 compare-and-swap | Stale old id refused (`stale ref`). Creating an existing ref refused. Force push, branch delete and default-branch delete are all allowed with a write token. |
| E4 ref namespaces | Pushes accepted and listed for `refs/notes/premise`, `refs/heads/green`, `refs/session/log`, a tag, and `refs/agents/a1/head`. All five could be fetched back with matching content. |
| E4 binding reads by name | `log` and `readFile` resolve short branch names (`green`) and tag names, and commit ids. They do **not** resolve full names (`refs/heads/green`) or other namespaces (`refs/notes/premise`, `refs/session/log`). Read those by commit id. |
| E5 fork | See the decision table. A push to a fork left the source unchanged. |
| E6 binding reads | `readFile`, `readTree`, `readCommit`, `readBlob`, `log`: about 110 ms each (p50). After a push, reads showed the new head within 109 to 274 ms. No stale read in 10 rounds. |
| E7 soak | 100 sequential commit-and-push cycles from one Durable Object: 0 failures; p50 128 ms, p95 278 ms, max 449 ms; 6.9 pushes per second. |
| E8 hand-built pack | Single-ref post 516 ms; two-ref post 362 ms (one sample each). An update that needs no new objects works with an empty pack. |

## E9: Workers AI tool loop

Task: read two small files, change a constant, update one call site, using two
tools. One run per model.

| Model | Correct | Model calls | Total | Median per call |
| --- | --- | --- | --- | --- |
| `@cf/openai/gpt-oss-120b` | yes | 5 | 3.6 s | 0.78 s |
| `@cf/moonshotai/kimi-k2.7-code` | yes | 5 | 4.1 s | 0.96 s |
| `@cf/zai-org/glm-5.3-flash` | yes | 3 | 5.1 s | 1.9 s |
| `@cf/deepseek-ai/deepseek-v4-flash-0731` | yes | 3 | 10.3 s | 3.9 s |
| `@cf/zai-org/glm-5.3` | yes | 3 | 28.2 s | 3.5 s |
| `@cf/qwen/qwen3.8-27b` | yes | 3 | 55.2 s | 23.0 s |

Request shape that works: `env.AI.run(model, { messages, tools: [{ type:
"function", function: { name, description, parameters } }], max_tokens })`. An
assistant message that carries tool calls must have a string `content`; `null`
is rejected with error 5006.

This task is far smaller than a real intent. It shows the request shape and
relative speed, not coding quality.

## Dynamic Worker isolate as a sealed test runner

The pool's simulation (shared rules, one creature, 3,000 ticks) was loaded as
modules into a Dynamic Worker with `globalOutbound: null`.

| Check | Result |
| --- | --- |
| Fresh isolate, load and run | 9 to 14 ms per run, nine different code versions |
| Network | `fetch()` inside the isolate throws |
| Runaway loop with `limits: { cpuMs: 50 }` | Stopped: "Worker exceeded CPU time limit." |
| Syntax error | Reported: "Unexpected end of input" |
| Missing export | Reported: "crab.spawn is not a function" |
| Concurrency | At most four Dynamic Workers in flight per Worker request (ten per Durable Object). A fifth is refused with a clear error. Run checks in sequence or four at a time. |

One result matters for the product claim. With the shared quantity rescaled
(`ENERGY_MAX` 100 to 1) and a creature still written for the old scale, the
generic invariants all **passed**: the crab simply hid for all 3,000 ticks. A
test suite that does not encode this creature's intended behaviour accepts the
merged code. The premise check is what catches it.

## Clef premise triage

Eight hand-made cases. Each gives Clef the intent, the old and new source of
something the agent read, and the agent's patch, and asks one yes/no question:
would the patch now behave incorrectly because it relies on the old meaning?

| Case | Expected | `clef` | `clef-flash` |
| --- | --- | --- | --- |
| Hard-coded threshold after a rescale | yes | 0.96 | 0.88 |
| Threshold written as a share of the constant | no | 0.08 | 0.31 |
| Equivalent rewrite of a helper | no | 0.03 | 0.11 |
| Speed unit changed from per second to per tick | yes | 0.98 | 0.80 |
| Unrelated constant changed | no | 0.01 | 0.08 |
| Pixel coordinates after normalising | yes | 0.93 | 0.87 |
| Hard-coded day length | yes | 0.95 | 0.76 |
| New optional parameter with a default | no | 0.04 | 0.06 |

- Both models put every case on the correct side of 0.5. `clef` separates the
  classes more widely (lowest "yes" 0.93, highest "no" 0.08) than `clef-flash`
  (0.76 and 0.31).
- Latency per call: 130 to 930 ms in this run. About 460 input tokens per call.
- A burst of 40 concurrent `clef-flash` calls: all 40 succeeded in 1.1 s.
- Eight cases written by the same author as the question are a smoke test, not
  a calibration. Thresholds must be set on a larger set that includes cases
  from real agent runs.
